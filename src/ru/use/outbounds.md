# Аутбаунды

[[~outbound|Аутбаунд]] — выход для трафика, дошедшего до узла: прямо в
интернет, в блокировку или дальше на другой прокси-сервер.
[[routing|Маршрутизация]] выбирает аутбаунд для каждого соединения. Аутбаунды
лежат в общем пуле в разделе **Конфигурации ядра → Исходящие** и доходят до
узлов через [[templates]].

## Когда он нужен {#when-you-need-one}

У каждого узла есть встроенный аутбаунд `direct`, и без правил маршрутизации
весь трафик уходит через него прямо к адресату. Большинству парков этого и
нужно. Аутбаунды добавляют, когда трафик должен идти куда-то ещё:

- **Заблокировать** что-то: рекламу, торренты, список адресатов.
- **Построить цепочку** через другой сервер: отправить часть или весь трафик
  дальше на вышестоящий прокси, чтобы интернет видел адрес этого сервера.
- **Выбирать между** несколькими вышестоящими серверами, вручную или по
  измеренной задержке.

## Типы {#types}

| Тип | Что делает |
| --- | --- |
| `direct` | Подключается к адресату прямо с узла. |
| `block` | Отклоняет соединение. |
| `socks`, `http` | Передаёт на SOCKS- или HTTP-прокси. |
| `shadowsocks`, `vmess`, `vless`, `trojan` | Передаёт на другой прокси-сервер с этим протоколом, со своим транспортом и TLS. |
| `hysteria`, `hysteria2`, `tuic` | Передаёт по QUIC на сервер с этим протоколом. |
| `shadowtls`, `anytls`, `ssh`, `naive`, `mieru`, `snell`, `sudoku`, `trusttunnel`, `tor` | Другие вышестоящие типы, для операторов, у которых уже есть такой сервер. |
| `masque` | Cloudflare WARP: трафик выходит через сеть Cloudflare, а не с адреса самого узла. См. [WARP](#warp). |
| `selector` | Группа других аутбаундов; используется один из них, выбранный вами. |
| `urltest` | Группа других аутбаундов; используется тот, у которого наименьшая измеренная задержка. |

Для вышестоящего прокси заполните адрес сервера, порт и учётные данные на
вкладках **Basic** и **Protocol**, а транспорт и TLS — на их вкладках. Вкладка
TLS предлагает **Нет**, **TLS** или **REALITY** — в зависимости от того, чего
ждёт дальний сервер.

`selector` или `urltest` перечисляет теги аутбаундов, из которых выбирает. Эти
аутбаунды должны быть в том же шаблоне.

Аутбаунд `tor` не запускает на узле никаких программ. Путь к исполняемому
файлу, дополнительные аргументы и транспортные плагины в его JSON
отклоняются при сохранении с указанием параметра, а у аутбаунда, сохранённого
с ними раньше, они отбрасываются по дороге на узел. Каталог данных хранится в
каталоге кэша узла, какой бы путь ни был указан.

## Добавление аутбаунда {#adding-an-outbound}

1. Откройте **Конфигурации ядра → Исходящие** и нажмите **Добавить**.
2. Выберите **Type** и задайте **Tag**. По тегу маршрутизация называет
   аутбаунд, и после создания он не меняется.
3. Заполните вкладки, которые показывает этот тип.
4. Нажмите **Сохранить**.
5. Выберите его в поле **Исходящие** шаблона и укажите в правиле
   маршрутизации или как **Исходящее по умолчанию**.

Аутбаунд, который не выбран ни в одном шаблоне, ничего не делает. Полоса
сводки учитывает такие в **Не используются**.

## Импорт аутбаундов {#import}

Кнопка **⋯** (**Операции**) рядом с **Добавить** открывает меню импорта.
**Из ссылок** превращает ссылки на серверы (`vless://…` и подобные) в аутбаунды: вставьте их по одной
в строке или одним блоком base64.

1. Вставьте ссылки и нажмите **Преобразовать**.
2. Прежде чем что-либо сохранится, показываются все строки: тег, тип,
   **Имя в источнике** и **Примечания**. Измените тег, где нужен другой;
   каждой строке нужен тег, которого нет ни у другой строки, ни у
   существующего аутбаунда. Снимите отметку со строки, чтобы её пропустить.
3. Нажмите **Добавить** *n*. Каждая строка создаётся обычным путём, тем же
   сохранением, что и **Добавить**, поэтому все проверки сохранения
   по-прежнему действуют. Строка, которую сохранение отклонило, остаётся в
   списке с причиной, чтобы её исправить и отправить снова.

Строка, которая не преобразовалась, указывается в **Не преобразовано** по
номеру, а не самой ссылкой, ведь в ссылке есть учётные данные. Ссылки naive
отклоняются: некоторые сборки узла не умеют naive. Ссылки создают только
аутбаунды: сервер WireGuard добавляется его файлом `.conf` на странице
эндпоинтов ([[endpoints#import]]). Ссылки не сохраняются. Новые аутбаунды пока
не входят ни в один шаблон: добавьте их в шаблон и напишите правила
маршрутизации, которые их используют.

## Cloudflare WARP {#warp}

Аутбаунд WARP выпускает трафик через сеть Cloudflare, и адресат видит адрес
Cloudflare вместо адреса узла. Это помогает с сайтами, которые не принимают
адрес вашего сервера.

1. Откройте **Конфигурации ядра → Исходящие** и нажмите **Из пресета**.
2. Выберите **Cloudflare WARP**. Откроется обычная форма с типом `masque` и
   тегом `warp`. Поля профиля оставьте пустыми; исключение — ключ WARP+
   ([WARP+](#warp-plus)).
3. Нажмите **Сохранить**, выберите его в поле **Исходящие** шаблона и сами
   напишите правила маршрутизации, которые отправляют трафик в `warp`. Пресет
   не добавляет правил.

Создавать аккаунт не нужно. При первом запуске каждый узел сам регистрирует
своё устройство WARP в Cloudflare и хранит его, так что два узла не делят один
аккаунт. Для этой первой регистрации узлу нужен доступ к API Cloudflare. Если
его нет, укажите в **Profile detour** аутбаунд, через который он есть.

Профиль, заполненный вручную (его ID и токен), указывает на одно устройство
WARP, на котором регистрируется узел. В шаблоне, который выполняют два или
больше включённых узла, все они делили бы это устройство, а оно хранит только
ключ последнего узла: туннель остаётся у одного узла, остальные перестают
подключаться. Панель сохраняет такой шаблон, но предупреждает о нём: его
строка на странице шаблонов показывает **Проверьте**, а редактор называет
аутбаунд ([[templates#checked-on-save]]). Вместо этого оставьте профиль пустым и
укажите ключ WARP+ либо назначьте каждому узлу отдельный шаблон. У полей
ключей WARP нет кнопки генерации: придуманное значение там никогда не верно.

### WARP+ {#warp-plus}

Ключ WARP+ переводит узлы на платный WARP Cloudflare. Вставьте его в поле
**WARP+ licence key** в форме аутбаунда и сохраните. Каждый узел привязывает
ключ к устройству WARP, которое у него уже есть; новое устройство не
регистрируется.

- Каждый узел — отдельное устройство, а ключ покрывает лишь несколько
  устройств (на момент написания — пять). Сверх этого Cloudflare отклоняет
  ключ, и узел остаётся на бесплатном WARP; причина видна в журнале узла.
- Если очистить поле, узлы не вернутся на бесплатный WARP. Это делает
  **Recreate profile**, с новым устройством на каждом узле.
- Узел, выпущенный до этого поля, отклоняет аутбаунд с ним. Обновите узлы до
  того, как задать ключ ([[start/update]]).

## Как маршрутизация ссылается на аутбаунд {#how-routing-names-an-outbound}

Маршрутизация ссылается на аутбаунд по тегу в четырёх местах:

- **Исходящее** в правиле маршрутизации;
- **Исходящее по умолчанию** шаблона, которое забирает все соединения, не
  попавшие ни под одно правило;
- другой аутбаунд, который подключается через него (detour);
- `selector` или `urltest`, в списке которого он есть.

Пресет маршрутизации **Блокировать торренты** добавляет собственный
аутбаунд `block` с именем `block-torrent`, который узел учитывает. См.
[[routing#presets]].

## Проверка аутбаунда {#checking-an-outbound}

**Проверка маршрута** в меню строки узла или пользователя проходит по
правилам маршрутизации узла для описанного вами соединения и называет
аутбаунд, который его заберёт. **Проверить и подключиться** вдобавок открывает
с узла одно настоящее соединение по этому пути и сообщает, был ли достигнут
адресат и сколько это заняло. Через вышестоящий прокси ответ может быть «не
отклонено, не подтверждено», потому что прокси не всегда сообщает, подключилась
ли его дальняя сторона. См. [[nodes]].

**Проверка исходящих** в меню строки узла перечисляет все аутбаунды и
эндпоинты, которые запускает узел. Список читается с самого узла, поэтому
встроенный `direct` и туннели тоже в нём. **Проверить все** или кнопка на
строке заставляет узел получить тестовый URL через этот аутбаунд и показывает,
сколько миллисекунд занял ответ, или ошибку узла; сервер, который так и не
ответил, даёт *timed out*. Оставьте **Тестовый URL**
пустым, чтобы использовать значение узла по умолчанию. Нужно право изменять
узлы, потому что проверка заставляет узел открывать соединения.

## Аутбаунд только для одного узла {#per-node-outbounds}

Аутбаунд попадает на узлы, шаблон которых его выбирает. Когда одному серверу
нужен вышестоящий сервер, которого нет у других, например другой выход для
одного региона, дайте этому узлу собственный шаблон, который его выбирает.
См. [[templates#a-template-of-its-own]].

## Изменение и удаление {#editing-and-deleting}

Изменение аутбаунда отправляется на все узлы, которые его содержат. Действие
**Дублировать** копирует аутбаунд под новым тегом.

Панель отказывается удалять аутбаунд, на который по тегу ещё что-то
ссылается в шаблоне, который его выбирает: правило маршрутизации, аутбаунд по
умолчанию шаблона, detour или группа. Она перечисляет эти ссылки.
Перенаправьте их, затем удаляйте. Аутбаунд с тегом `direct` удаляется всегда,
потому что у каждого узла есть свой встроенный `direct`. Узел
тоже отказывается убрать аутбаунд, который ещё нужен его текущей
маршрутизации, поэтому изменение, удаляющее аутбаунд и правило, которое на
него ссылается, нужно сохранять вместе.
